# 问题与解决

按现象记录，便于日后定位同类问题。条目为追加式维护。

## Windows Cloud Files API

### 非 packaged 进程下没有原生右键动词与状态图标

**现象**：同步根在资源管理器里出现了导航树节点与「状态」列，但右键没有
「始终保留在此设备上」/「释放空间」之外的云提供商动词，云朵状态角标也无法
通过 `StorageProviderSyncRootManager` 单独补齐；MSIX + 稀疏包（sparse package）
才能拿到更深的外壳集成。

**原因**：Cloud Files 的深度外壳集成（右键动词、角标）依赖 packaged identity
（包标识）。本项目走 portable / Velopack 分发，没有 MSIX 包标识，因此
`StorageProviderSyncRootManager.Register` 拿到的只是「已注册同步根」这一档集成。

**现状与补偿**：应用内自带管理台（`native-sync-manager` 窗口，标题「同步资源浏览器」）
承担状态呈现与「固定 / 取消固定 / 释放空间」等操作，即 D-7 管理台是产品补偿路径。
改走 MSIX + 稀疏包需要签名就绪，列为 1.3.0 候选（ADR-108）。

### 占位符创建必须在提供程序连接进程内

**现象**：从外部进程（探针程序）对同步根调用 Cloud Files API 会被拒绝，
返回 `0x8007018B`（已拒绝访问云文件）。

**原因**：Cloud Files 只允许**已连接该同步根**的提供程序进程发起占位符操作。

**解决**：占位符创建与 `sync_now` 必须在同一个进程内完成（生产实现已满足：
`sync_now` 由应用进程执行，且 `connect()` 先建立连接）。

### 空目录残留：被 cldflt 锁住的目录删不掉，重启可清

**现象**：删除同步根下的空目录（或曾经的占位符目录）时报「正在使用中」，
资源管理器也删不掉；重启系统后可以正常删除。

**原因**：`cldflt` 驱动会在内核侧短暂持有目录句柄，用户态删除会失败。

**现状**：属已知残留行为，不影响功能；需要清理时重启后删除。
应用侧对「本地已不存在的条目」不再调用平台删除接口（见下一条），避免因此中断整轮同步。

### 远端删除对账时对不存在的本地路径调用删除接口会中断整轮同步

**现象**：远端删除一个目录后，`sync_now` 在删除其子项时 `ENOENT`，整轮同步中断，
表现为「只剩目录、没有文件」。

**解决**：`sync_now` 的远端删除对账在调用 `remove_placeholder` 前先判断本地路径是否
仍存在；已不存在的条目**直接记账**（`tombstone`），不再调用平台接口。

### 路径归一化：只有反斜杠的根路径会让根内合法路径被判越界

**现象**：回调里由 `CF_CALLBACK_INFO.NormalizedPath` 与同步根做前缀比较时，
若同步根以 `C:\...` 形态传入（未先做分隔符替换），剥离盘符后会残留一个前导
分隔符，`strip_prefix` 失配 → 根内合法路径被判定越界，召回被拒。

**原因**：`NormalizedPath` 不含盘符（形如 `\Users\someone\...`），而同步根一定是全路径；
两边的规范化顺序不一致时就会出现「一侧有前导分隔符、另一侧没有」。

**解决**：把路径归一（去 `\\?\` 前缀、去盘符、统一 `/`、去前导分隔符）收敛到一个
纯函数，并且**删除 platform 内的重复实现**——生产路径与单测现在共用同一份实现，
避免再次分叉（ADR-109 记录）。

### 占位符创建方式：`MARK_IN_SYNC` + 满尺寸磁盘数据不会被 Explorer 召回

**现象**：双击占位符打开 zip 报「格式未知或损坏」；本地文件是 103276 字节全零，
属性为 PINNED + REPARSE_POINT。

**原因**：`File::create` + `set_len(size)` + `CfConvertToPlaceholder(CF_CONVERT_FLAG_MARK_IN_SYNC)`
让 Windows 认为内容已在本地，双击不触发 `FETCH_DATA`，消费者读到全零。

**解决**：在线占位符必须**无磁盘数据**——改用 `CfCreatePlaceholders` 通过
`CF_FS_METADATA` 声明 `FileSize`，`Flags = NONE`，由平台按需召回。

## NativeSync 状态与一致性

### 重启后内存映射丢失导致召回被拒

**现象**：生产日志 `native-sync fetch rejected: unmapped file request_key=0`，
重启应用后双击占位符打不开。

**原因**：`fs_id → (RemotePath, relative)` 映射只在 `sync_now` 时建于内存，重启即丢；
SQLite 里其实已有全部数据但未被回调解析使用。

**解决**：回调的身份解析链改为「内存映射 → SQLite 按 `fs_id` 回退（在 worker 线程内）
→ 自愈写回内存」，并在 `connect()` 成功后从 SQLite 预热内存映射。

### 本地变更捕获引入的「无声复活」风险（S1 的 H1）

**现象（若不做守卫）**：注册 `NOTIFY_DELETE` / `NOTIFY_RENAME` 之后，`sync_now`
会同时看到「本地已删除/改名」与「云端仍在」，旧逻辑会把云端条目重新建回占位符——
用户删掉的文件在下次同步**无声复活**，改名则多出一个**旧路径副本**。

**解决**：`sync_now` 跳过 `pending_op ∈ {delete, rename}` 条目的占位符重建，保留
pending 并计入 `attention_entries`；同时仍登记进本轮 `seen`，避免被
`missing_entries` 误判为远端删除。见 ADR-109 §6、§8。

### 应用自身的 CF 操作会产生「自杀回调」

**现象（若不做守卫）**：`sync_now` 因远端删除而删除本地占位符，随之而来的
`NOTIFY_DELETE` 被记成「用户删除了文件」，产生假的待同步条目。

**解决**：应用自身的 `dehydrate` / `remove_placeholder` / 水合都先立守卫
（路径 + fs_id，30s TTL，一次操作只抵消一次通知）；命中事件 `source="app"`，
只留痕、不产生 `pending_op`。见 ADR-109 §4。

### 日志落盘：依赖 crate 的 `log::info!` 不会写进应用日志文件

**现象**：`%LOCALAPPDATA%\com.weyham.pandock\logs\Pandock.log` 长时间没有新内容，
nativesync 的诊断日志看不到，故障排查链路不可用。

**原因**：日志插件对依赖 crate 的 target/level 过滤未覆盖 `pandock_nativesync`。

**解决**：放宽日志插件的 target/level 覆盖范围，使 nativesync 的
`info`/`warn` 真正落盘（fetch start/done/failed、notify kind/source 等）。

### 一次性守卫不复位：功能在「停用 → 启用」后静默哑掉

**现象（本次终审发现，S1 引入）**：用户点一次「停用 NativeSync」再点「启用同步」
（或任何 `disconnect → connect` 循环）之后，本地变更捕获**永久失效**，直到重启应用；
日志里一行都不留。

**原因**：`stop_notify_worker` 只把投递通道置空、**没有复位** `notify_worker_started`；
下一次 `start_notify_worker` 在 `swap(true)` 处直接返回，既不建通道也不起线程，
而投递函数拿到空 sender 就**静默** `return false`。

**解决**（三层，缺一层都还会静默）：

1. 停止时在同一临界区顺序内完成「置空通道 + 复位生命周期标记」；
2. 启动时以**通道是否存在**为权威判据（标记只用于挡并发重复启动），
   即使将来某条路径漏了复位也会重建通道；
3. 投递失败不再静默——通道缺失/断开时限频 `warn`（60s 一次），
   让这类失效在日志里可见。

**通用教训**：任何「一次性守卫 + 可重复执行的启动路径」都必须成对复位，
并且**失败路径必须有日志**。只有内部函数的单测不足以发现这类缺陷——
回归测试必须从**真实入口**（停止/启用开关）走一遍 start → stop → start，
并且要在还原缺陷实现后确认测试真的会失败。

### 开发部署用相对路径命中陈旧构建，且源目标自校验无法发现"源错了"

**现象**：`scripts/deploy-dev.ps1` 报「部署完成」，脚本的部署后哈希复核也通过，
但 `app\pandock.exe` 实际是**另一份陈旧构建**——被审 HEAD 的产物（44,449,791 B @ 当天 10:39:33，
sha256 `c609fc68…`）没有被部署，进去的是同期另一工作树里 10 天前的产物
（43,853,303 B，sha256 `1e8be974…`）。表现是：日志缺 `native-sync notifications effective=…`、
`sync.db` 没有发生 v3 迁移、也没有同步根注册行——**验收会全员假绿**。

**原因**：部署命令先切到**主工作树**再传**相对路径** `-SourceDir .\target\velopack-stage`，
于是相对路径解析到主工作树里遗留的陈旧 stage 目录。而脚本的哈希校验是
`Get-FileHash(源) == Get-FileHash(目标)`——**源与目标自校验只能证明"复制正确"，
永远无法证明"复制的是被审的那份产物"**。

**解决与通用教训**（三条，缺一条都可能再次发生）：

1. **部署必须用绝对路径指定 `SourceDir`，并校验源的「身份」**：
   绝对路径 + 产物大小/mtime + sha256（可对上被审 HEAD 的构建记录）。不要用相对路径，
   也不要依赖"我当时在哪个目录"这种隐式状态。
2. **源=目标的自校验不是发布校验**：它只覆盖复制环节。任何"部署成功"的判据里，
   必须包含**与被审产物对齐的身份校验**，否则复制得再正确也可能是错的源。
3. **部署后必须再验一个"只有新构建才满足"的特征**，才算过门禁。本项目的现成特征：
   - 运行日志出现 `native-sync notifications effective=`（S1 起才有）；
   - `data/native-sync/sync.db` 的 `schema_migrations` 含本次迁移版本号、新表/新列存在；
   - 必要时在二进制里查特征串（本项目用过 `pandock://nativesync/change` 等）。
   凡是"旧构建也能满足"的判据（进程存活、目录可访问、占位符存在）都不能用来证明部署成功。

**另一条相关教训（门禁设计）**：`.bak` 的**时间戳不能**用来证明"这次迁移前确实备份过"——
Windows 的 `CopyFileEx` 覆盖已存在文件时会**保留目标原有的创建时间**、并**复制源的 LastWriteTime**，
所以 `sync.db.bak` 的 mtime/ctime 都可能停留在很久以前。
门禁应以「迁移后数据仍在（条目数/状态分布不变）」+ 一份**独立的一致性快照**为准，
而不是以 `.bak` 的时间戳为准。

### 注销同步根会把占位符转成普通文件、未水合的会被永久删除

**现象**：用户从托盘**正常退出**应用后，`D:\Documents\Pandock` 整棵树（4 个目录 + 3 个文件）
全部不再是 Cloud Files 占位符（`fsutil reparsepoint query` → Error 4390；attrs 无 `0x400`），
只有同步根本体还是占位符（Tag `0x9000301A`）。索引仍标 `placeholder=1`，事实与索引不一致；
资源管理器**没有任何云状态可显示**（无角标 / 无按需下载 / 无「释放空间」）。

**用户可观测症状**（与上面的 `fsutil` 实测互为印证）：在资源管理器里对 `db.sql` 右键，
**「释放空间」是灰调、点不了**——普通文件没有这个云动词；同时也没有任何云状态角标。
诊断顺序建议：先看**右键菜单动词是否可用**（用户可自述），再用 `fsutil reparsepoint query` 确认磁盘事实。

**原因**：`Drop(退出) → disconnect() → unregister_from_shell()`。而注销同步根（`CfUnregisterSyncRoot`
或外壳的 `StorageProviderSyncRootManager.Unregister`）会**遍历整棵同步根**：
已水合的占位符**转回普通文件**、**未水合（仅在线）的占位符被从本地永久删除**、
已填充的占位符目录转回普通目录、未填充的目录被永久删除。实测形态与官方文档逐条吻合。

**教训**：
1. **"注销同步根"是破坏性操作**，语义上等同"移除同步根"，绝不能放在**退出路径**里；
   退出只应断开引擎（`CfDisconnectSyncRoot`）。
2. **"停用同步"必须是非破坏的**：默认停用只断开引擎，不注销。注销只留给显式的
   "从资源管理器移除同步根 / 卸载"，且必须向用户告知风险。
3. 判定"注销是否是致因"的一个便宜方法：**对比"强杀 vs 正常退出"后同步根注册表键是否还在**
   （强杀不会触发退出路径，键应保留），并同时看日志里有没有注销行。
4. 索引里记着 `placeholder=1` **不等于**文件系统上还是占位符——排查此类问题必须用
   `fsutil reparsepoint query` / 属性位核对**磁盘事实**。

**可观测性决策（同事故的延伸）**：占位符的 **in-sync 状态没有任何外部只读路径**——
CFAPI 只有 `CfSetInSyncState`（**没有** `CfGetInSyncState`），外部进程调用被 `0x8007018B` 拒，
`fsutil` 不暴露该状态，索引库也不记录。而该状态一旦为「未同步」，Explorer 会**禁用「释放空间」**
并显示"同步挂起"箭头（正是用户反复反馈的现象）。因此本仓库改为**进程内常驻告警**：
在占位符创建/自愈与 `sync_now` 的每条目处理之后，用
`CfGetPlaceholderInfo(CF_PLACEHOLDER_INFO_BASIC).InSyncState` 只读探测一次，
**仅在不是 `IN_SYNC` 时 `warn`**（`native-sync in-sync probe not_in_sync=true kind=<file|dir>`），
正常与查询失败走 `debug`；只记 kind、不记文件名。

**配套自愈**：`create_placeholder` 对"已存在但不是占位符"的路径改用
`CfConvertToPlaceholder`（identity = fs_id、`MARK_IN_SYNC`）**就地转回占位符**，保留内容与 PINNED 位；
这是修复此类脱云状态的唯一非破坏手段（用户点一次「立即同步」即可修复）。

**已知残留风险**：`connect()` 失败时的回滚仍会注销（避免留下"已注册但未连接"的不可访问目录），
若根上已有未水合占位符，该回滚会永久删除它们——已列为后续工作项。

### 蓝色循环箭头 = 占位符处于 NOT_IN_SYNC，且 S1 没有任何方向会把它清回已同步

**现象**：状态列里某些占位符显示**蓝色循环箭头**（未同步），其余显示绿色勾；右键菜单里
**「释放空间」对被标成未同步的占位符是灰的**（平台不敢脱水一份"状态未知"的数据）。
索引侧看不到任何对应记录：`local_change=0`、`pending_op` 全空、本地 mtime/size 与云端一致。

**机制**：in-sync 是**平台侧**状态。S1 是"只读召回 + 本地变更捕获"，**没有上传方向**，
所以一旦某个占位符被平台标成未同步（历史注销/重放、或写入后未回写等），
**没有任何代码会把它恢复**——于是永久卡蓝箭头、动词永久灰掉。这正是用户反复反馈的现象。

**修复（in-sync 自愈）**：`sync_now` 处理每个条目后，**三个前置条件全部满足**才动手：
1. 本地路径存在且**是**占位符；
2. 该条目**没有**已记录的本地改动（`pending_op` 为空）；
3. 本地 `mtime`/`size` 与快照**一致**（内容与云端一致）。
满足后再读平台侧状态：**只有不是 `IN_SYNC` 时**才调用 `CfSetInSyncState(IN_SYNC)`
（日志 `native-sync in-sync repaired fs_id=… kind=…`）；已是 `IN_SYNC` 走 `debug`，读不到状态则**不动手**。
**判据缺一不可**：任何"内容可能被本地改过"的情形下强行置为已同步，会把真实改动**伪装成已同步**
（S1 没有上传方向，用户会误以为改动已上云），比现状更危险。
判定逻辑抽成纯函数 `in_sync_repair_action`，单测覆盖三条负例与"已是 IN_SYNC 不调 set"。

**产品代码里的同类陷阱（已修）**：同一现象也存在于**应用自身**——自愈判定原先读 `MetadataExt::file_attributes()`（= `GetFileAttributesW`），而该读取路径**不返回 `0x400`**（同期 PowerShell 走的 `GetFileAttributes*` 路径却返回；**机制未确定**，可能取决于底层 API 不同——不要写成「Windows 隐藏该位」这类一般化断言），于是**健康占位符会被误判成普通文件**，每次 `sync_now` 都重复调用 `CfConvertToPlaceholder`（白折腾，并很可能就是个别条目被重置成 NOT_IN_SYNC 的机理）。已改为**CF 原生判定**：`CfGetPlaceholderInfo(CF_PLACEHOLDER_INFO_BASIC)` 成功即视为占位符；通用属性位仅作为 `debug` 诊断线索打印（`attrs=0x… attrs_hint=… cf_placeholder=…`）。回归测试 `generic_attribute_bits_are_not_a_reliable_placeholder_signal` 固定住这个陷阱。

**排查教训（重要）**：判断"是否占位符"**必须用 `fsutil reparsepoint query` 或 PowerShell 的属性**；
实测 **Python 的 `st_file_attributes`（以及 Rust 的 `MetadataExt::file_attributes()`）这条读取路径不返回 `FILE_ATTRIBUTE_REPARSE_POINT`**，而同期 PowerShell 的属性读取返回；**机制未确定**（可能底层 API 不同），（读到 `0x100020`
而 `fsutil` 明确显示 `Reparse Tag 0x9000601a`），一度让人误判"树在部署前就已脱云"。
**唯一可信的是 `fsutil`。**

### 云占位符判定把"不确定"当成"不是"，导致对目录误转换并放大为命令失败

**现象**：设置页 NativeSync 区块出现红框
`无法读取 NativeSync 状态：NativeSync: Cloud Files API: 云操作无效。(0x8007017C)`。
插桩（命令边界 + CF 调用点 warn）落地后，日志立刻定点：
```
WARN native-sync self-heal convert-to-placeholder failed: D:\Documents\Pandock\cc-switch-sync hr=0x8007017C
```
`0x8007017C` = `HRESULT_FROM_WIN32(ERROR_CLOUD_FILE_INVALID_REQUEST = 380)`（权威：windows 0.58 绑定）。
而该目录**本来就是占位符**（`fsutil` → `Reparse Tag 0x9000601a`）——即对健康占位符发起了转换。

**根因（两层）**：
1. **错误映射过激**：判定用 `CfGetPlaceholderInfo(...).is_ok()`，把**任何**错误都当成"不是占位符"；
   该调用在这个目录上返回错误 ⇒ 判为"不是" ⇒ 触发误转换。**"不确定"被当成了"确定不是"，保守方向写反了。**
2. **失败放大**：误转换的 `INVALID_REQUEST` 被**冒泡**成命令错误，整条对账/状态路径一起失败（UI 红框）。

**修法**：
- **三态** `Placeholder | NotPlaceholder | Unknown` + 纯函数 `classify_placeholder_probe(Result<(), u32>)`：
  **只有** `ERROR_NOT_A_REPARSE_POINT (0x80071126)` 与 `ERROR_CLOUD_FILE_NOT_UNDER_SYNC_ROOT (0x80070186)`
  判为 `NotPlaceholder`；**其余一切（含 INVALID_REQUEST / ACCESS_DENIED / NOT_A_CLOUD_FILE）→ `Unknown`**；
- `Unknown` = **视为占位符、不转换**（与"打不开文件句柄"同一保守策略），并
  `WARN native-sync placeholder probe inconclusive op=CfGetPlaceholderInfo hr=0x…`；
- **尽力而为**：转换失败只 `WARN` 后 `Ok(())`，继续处理其余条目，命令照常成功；
- 单测 `placeholder_probe_classification_is_conservative` 覆盖成功 / 两类"确定不是" / 五种"不确定"（含事故值）。

**已知限制（如实登记）**：目录上 `CfGetPlaceholderInfo` 的失败原因**未证实**（已知未知项）；
因 `Unknown` 一律不转换，**行为是安全的**；代价是**目录**的占位符判定与 in-sync 探测不可靠
⇒ **目录不参与自愈**；每次对账会留下 `placeholder probe inconclusive op=CfGetPlaceholderInfo hr=…`
的 warning 作为证据，供后续单独立项查证。

**防再犯**：判定类逻辑一律"**三态 + 明确 Unknown 处置 + 纯函数单测**"；系统调用错误必须能分类到
"确定/不确定"，且"不确定"的默认动作必须是**不改动现状**；任何"修复尝试"都必须 best-effort，
**不得把单条失败放大成命令失败**。
### 工具教训：PowerShell 的 `cd` 不改 .NET 的当前目录，相对路径会写到别的工作树

**PowerShell 的 `cd`/`Set-Location` 只改 `$PWD`，不改 .NET 的 `[Environment]::CurrentDirectory`。**
因此 `[System.IO.File]::WriteAllText("相对路径", …)` **不会**写到 `$PWD` 下的目标，
而是写到**进程启动时的工作目录**——在本仓库的多 worktree 布局下，这可能是**另一个 worktree**
（真实事故：一次文档追加把文件写进了主工作树 `F:\Projects\Weyham\baidupan-shim\docs\`）。

**规则**：
1. **所有文件读写一律用绝对路径**（本仓库有多个 worktree，相对路径尤其危险）；
2. 若必须用相对路径，先在 PowerShell 里 `[Environment]::CurrentDirectory = $PWD` 或显式 `Resolve-Path`；
3. 写入前后各核对一次**目标路径归属**（`git -C <worktree> ls-files --error-unmatch <path>` 可判断是否被跟踪）；
4. 事故现场的清理要**先请示**（本次由总监核对归属后删除）。
### 显式 UNPINNED = 向平台登记"待脱水"，导致资源管理器显示同步挂起且「释放空间」灰显

**现象**：`db.sql` 在资源管理器里是**蓝色循环箭头**（同步挂起），右键「释放空间」**灰显**；
而 CF 层实测完全健康——总监用外部只读探针拿到真值：
```
CfGetPlaceholderInfo(CF_PLACEHOLDER_INFO_BASIC)
  db.sql         hr=0x0  pin=2(UNPINNED)    inSync=1(IN_SYNC)
  manifest.json  hr=0x0  pin=1(PINNED)      inSync=1(IN_SYNC)
  skills.zip     hr=0x0  pin=0(UNSPECIFIED) inSync=1(IN_SYNC)
  cc-switch-sync hr=0x0  pin=0             inSync=1(IN_SYNC)   ← 目录也成功（读探针不要求提供程序进程内）
CF_PLACEHOLDER_INFO_STANDARD：db.sql FileSize=52699 OnDiskDataSize=52699 ⇒ 已完整水合
shell 侧：System.FilePlaceholderStatus db.sql=14 / manifest.json=15；唯一差异是 pin
```

**文档依据（MS Learn `CF_PIN_STATE`）**：
- `PINNED(1)`：**"the platform will fail any dehydration request on pinned placeholders."**
- `UNPINNED(2)`：**"The sync provider will be notified to dehydrate/invalidate the placeholder's content on-disk asynchronously after the unpin request is received"**
- `UNSPECIFIED(0)`：**"The platform can decide freely when the placeholder's content needs to present or absent locally on the disk."**

⇒ **显式 UNPINNED 的语义本身就是"请提供程序异步脱水"**。一个显式 UNPINNED 且内容仍在本地（上表 `OnDiskDataSize == FileSize`）的占位符，
在平台看来就是"**有活没干**" ⇒ 资源管理器显示同步挂起类图标、且「释放空间」对该条目**没有意义**（已在待办里）⇒ 灰显。
`PINNED` 与 `UNSPECIFIED` 的条目则表现正常。

**代码里唯一的显式 UNPINNED 写入点**：
- `platform.rs` 的 `pin()`：`pinned ? CF_PIN_STATE_PINNED : CF_PIN_STATE_UNPINNED` → `CfSetPinState`；
- 唯一调用方是 `manager.rs` 的 `EntryAction::Unpin`（界面上点「取消固定」）⇒ 除此之外应用不会把用户的文件置为显式 UNPINNED；
- `sync_now` 的 pin 回读只写我们自己的索引（不碰文件系统）；`CfConvertToPlaceholder`（自愈）不传 pin 标志 ⇒ 结果为 UNSPECIFIED。
⇒ `db.sql` 变成 UNPINNED 的最可能来源：**用户过去对它点过一次「释放空间」**（ADR-108 时期的脱水实验就在这个文件上），
平台据此登记"待脱水"并一直等提供程序执行。

**修法（脱水后 pin 归一）**：一次**成功脱水之后**，若脱水前的 pin 是显式 `UNPINNED`，则调用
`CfSetPinState(CF_PIN_STATE_UNSPECIFIED)` 把它归回"平台自由决定"——因为"请脱水"这件事已经完成，留着它就是永久的待办。
判定抽成纯函数 `dehydrate_post_action(pin_state) -> NormalizeToUnspecified | LeaveAlone`，
单测覆盖三例（**PINNED 不动** / UNPINNED 归一 / UNSPECIFIED 不变）。
**不得**覆盖用户的显式 PINNED（固定是明确的"保留本地"意图，且平台本就会拒绝对 PINNED 的脱水）。

**教训（写给后来者）**：**判断云状态必须用 API 真值，不能从图标反推**——
本轮多次"从图标推断根因"都偏了；而一次只读的外部探针（`CfGetPlaceholderInfo`）
就把 `pin/inSync/OnDiskDataSize` 全部说清，且**读探针不受"必须在提供程序进程内"的限制**。
### D1：我们自己的元数据调用把刚脱水的文件又读回来了（"释放空间"当场被撤销）

**现象与证据（真机）**：用户点「释放空间」后，同一秒出现
```
08:18:34 INFO native-sync pin normalized to UNSPECIFIED after dehydration (was UNPINNED)
08:18:34 INFO native-sync fetch start fs_id=1071335884273132 offset=0 length=52699
08:18:36 INFO native-sync fetch done  fs_id=1071335884273132 bytes=52699 full_file=true
```
外部只读探针最终实测 `OnDiskDataSize = 52699`（= FileSize）⇒ **内容又回到本地**，用户看到的只是"从挂起变成本地可用"，
**始终没变成云朵**。

**根因**：`file_handle` 原先用 `FILE_GENERIC_READ | FILE_GENERIC_WRITE`。**对已脱水的占位符做数据访问**
会让平台立刻把内容物化回来——于是脱水成功后，我们紧接着的 `mark_in_sync` / pin 归一（同一个句柄）**撤销了刚完成的释放**。

**修法**：
1. **CF 元数据调用只用属性访问句柄**：只读 `FILE_READ_ATTRIBUTES`、改属性 `FILE_WRITE_ATTRIBUTES`；
   写入类操作（如 `CfSetPinState`）必须用**可写属性**句柄（`pin()` 曾误用只读句柄，是"管理台点击固定没有反应"的高度可疑根因）。
2. **顺序修正**：脱水 → **先验真** `CfGetPlaceholderInfo(STANDARD).OnDiskDataSize == 0` → **再**归一 pin；
   验证不过 ⇒ `warn`（含 op 与实测值）+ 保留 pin + **返回可感知失败**（禁止"看起来成功、其实没释放"）。
3. **校验读取不得触发水合**：`EntryAction::Dehydrate` 的 md5 校验前先查磁盘真值
   （新增只读 `on_disk_data_size`）；**已脱水则跳过 `std::fs::read`**（原前置只依赖索引 `state`，可能滞后于磁盘）。

**教训**：句柄的访问权限不是"够用就行"——**过宽的权限会以副作用的形式撤销用户刚完成的操作**，且完全无声。
凡是"元数据/状态"类调用，一律只请求属性访问。

### D2：ACK 回传平台指针，导致外部发起的脱水请求卡住（Explorer「释放空间」挂在半路）

**现象与证据（真机）**：外部进程调 `CfDehydratePlaceholder(h, 0, -1, NONE, NULL)`（写权限句柄，打开成功）
**阻塞 >60 秒不返回**，直到手工中断；同时应用日志出现
`notify kind=dehydrate phase=intent source=explorer reason=Some("user_manual")` ⇒ 回调跑了、也 ACK 了，**但调用方始终没返回**。

**根因**：`ack_dehydrate` 把 `FileIdentity` 设为 `info.FileIdentity` —— 那是**平台自己的缓冲区指针**，
而 ACK 里的 identity 应当是**提供程序自备的数据**；`ParamSize` 也不含任何内联 blob。平台因此没有接受这个 ACK。

**修法**：ACK 时 **`FileIdentity = null`、`FileIdentityLength = 0`**（不传身份）；
并把 `ack_operation` 里 `let _ = CfExecute(...)` 改为 **失败 `warn`（含 HRESULT）**——
ACK 失败会让调用方一直等下去，绝不能静默。

**文档依据（MS Learn 原文）**：
- `CfSetInSyncState`：*"An attribute or no-access handle is sufficient. The caller must have **WRITE_DATA or WRITE_DAC** access to the placeholder."*
- `CfSetPinState`：*"An attribute or no-access handle is sufficient. The caller must have **READ_DATA or WRITE_DAC** access to the placeholder. Otherwise, the operation fails with **STATUS_CLOUD_FILE_ACCESS_DENIED**."*

**D2 机理更正 + 乙-① 实现（2026-10-12）**
- **机理**：`CF_OPERATION_TYPE_ACK_DEHYDRATE` 的语义是 *Acknowledge **and dehydrate*** ——
  **脱水动作必须由提供程序完成**；平台在收到 ACK 之前一直阻塞发起方。
  此前我们只 ACK、不做脱水 ⇒ 平台在等一个永远不会发生的动作 ⇒ 发起方无限等。
  这解释了「我们自己发起的脱水成功（我们直接调了 `CfDehydratePlaceholder`）、外部发起的卡死」。
  两次 identity 尝试（平台的 `info.FileIdentity` 指针 / `null`）**都挂** ⇒ identity 不是那个变量。
- **实现（乙-①，单变量实验第 1 次）**：`on_notify_dehydrate` 里**先自己把脱水做掉**：
  属性句柄 → `CfDehydratePlaceholder` → **验真 `OnDiskDataSize == 0`** → 再 ACK；
  `CompletionStatus` 按结果给（成功 `STATUS_SUCCESS`；失败或验真不过 `STATUS_CLOUD_FILE_*`）。
  成功也留 info（脱水 HRESULT + ACK 状态 + 耗时），便于判定「≤1 秒返回」。
- **安全守卫**：①有未同步本地改动（`pending_op`，经 `crate::pending` 内存镜像在**回调线程 O(1)** 判定、
  不查库）⇒ **拒绝脱水** + ACK `STATUS_CLOUD_FILE_NOT_IN_SYNC` + warn，防"把用户没上传的改动丢掉"；
  ②路径解析不到 / 句柄打不开 ⇒ **照旧 ACK** + warn（绝不能让 Explorer 无限等）；
  ③自杀回调（我们自己的调用触发的通知）只确认、不再脱水（防自我递归）。
  镜像在启动/重连时由 `db.pending_fs_ids()` 预热，写入点只有 `db.set_pending_op` 一处。
- **候选 ②**（ACK 回传**我们自己的** 8 字节 `fs_id`）已落盘但
  `ACK_DEHYDRATE_WITH_OWN_IDENTITY = false`（默认关闭；与 ① 同一批落盘，**实验单变量**）。

**裁决结果：走方案甲——不注册脱水回调（2026-10-12）**
- **乙-① 实测（迭代第 1 次部署）**：回调里先自己 `CfDehydratePlaceholder` 再 ACK 的路径**功能成立**
  （真机日志 `dehydrate inline kind=done hr=0x00000000 on_disk_bytes=Some(0)`、
  `dehydrate ack kind=done status=0x00000000`，探针复核 `db.sql OnDisk == 0` ⇒ **空间确实释放了**），
  **但从通知到 ACK 耗时 53,597 ms（53.6 秒）** —— 资源管理器会像死了一分钟，**不可接受**。
  加上"两次 identity 尝试（平台指针 / null）都挂"，可判定 identity 不是变量：
  真正的问题是「脱水必须由提供程序完成，而在回调里完成它的代价极高」。
  **该实现已从生产路径回退**，只作为「已实测可行但 54 秒，未采用」的记录。
- **决策**：**不注册** `NOTIFY_DEHYDRATE` / `NOTIFY_DEHYDRATE_COMPLETION`（官方文档明说
  *"Implementation of this callback is optional"*）。不注册 ⇒ 平台自行完成外部/系统发起的脱水，
  不再有调用方阻塞在我们这里；**脱水事实由下一轮 `sync_now` 的磁盘真值对账得到**（见上文对账口径）。
- **代价与前置守卫（必做，不是可选项）**：失去「即将脱水」的拦截点后，**未上传的本地改动**
  可能被系统脱水直接丢掉（S1 没有上传方向）。因此：
  1. **捕获到本地内容改动（`pending_op = upload`）时，立刻对该占位符
     `CfSetInSyncState(NOT_IN_SYNC)`** —— 平台对 `NOT_IN_SYNC` 的占位符**拒绝脱水**；
  2. `sync_now` 对「库里仍有 `pending_op`」的条目**重新标记**（收敛路径），覆盖老库行与重启后遗留；
  3. 应用内「释放空间」(`EntryAction::Dehydrate`) 仍然**跳过** `pending_op` 非空的条目。
- **S1 边界（诚实状态）**：S1 无上传方向 ⇒ `NOT_IN_SYNC` **可能长期保持**，资源管理器会一直显示
  「同步挂起 / 蓝箭头」。这如实表示「本地有未同步改动」；等 S2 上传成功后清回 `IN_SYNC`
  （或由 `sync_now` 的自愈在「无本地改动且内容与云端一致」时恢复）。

**更正（迭代 2 实测，同日）：上面这条"不注册 ⇒ 平台自行完成脱水"**是错的**。**

## 自愈对"丢了身份的占位符"不生效：索引知情判定（2026-10-13）

**现象**：`skills.zip` 脱云成普通文件（占位符身份丢了）后，点「立即同步」**不自愈**：
日志 `existing-path probe checked=7 placeholders=6 converted=0`，伴随 2 条
`placeholder probe inconclusive op=CfGetPlaceholderInfo hr=0x80070178`。

**根因**：探测（`CfGetPlaceholderInfo`）对**普通文件**返回一个"确定不是占位符"类的错误，
但 `0x80070178` 不在我们写死的两个码里 ⇒ 被判成"不确定" ⇒ 保守不转换 ⇒ 自愈跳过。
⇒ 这套探测对"健康占位符"与"丢了身份的占位符"**无法区分**，而自愈要修的恰恰是后者。

**修法（开发总监给定，按此实现）**：探测判定保留三态，新增**索引知情**分支——
`Unknown + 有索引条目 ⇒ 就地转回占位符`（该路径曾经在索引里 ⇒ 曾经是云端同步来的占位符）；
`Unknown + 无索引条目 ⇒ 不动作`（本地新建文件不归自愈管）。
**不扩充错误码清单**（那是无底洞）；`0x80070178` 的语义**未能定位其文档**，故走"索引知情"判定（不许编）。
误判代价可接受：`CfConvertToPlaceholder` 对健康占位符只返回 `INVALID_REQUEST`（无害）。
**止血闸门只挡"探测型 NotPlaceholder"**；索引知情分支的证据来自**索引**（不是探测），故不受其节制。

**测试**：四分枝（占位符→不转换 / 确定不是→转换 / 不确定+有索引→转换 / 不确定+无索引→不动作）。

**顺带自检**：那两条 warn 是同一次对账里**同一个文件被探测了两次**——两条独立调用路径
（`create_placeholder` 的转换探测 + `repair_in_sync_if_needed` 的 is_placeholder 输入）各探一次；
共享一次探测结果会耦合两个独立调用点，按总监口径**可接受、写明即可**。
