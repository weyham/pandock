# ADR-111：无感同步（S1.5）设计——云变 → 本地自动跟上

- 状态：**已终审**（2026-10-13，开发总监终审通过，§6 决策点全部裁决）
- 日期：2026-10-13
- 关联：ADR-108（同步根外壳注册）、ADR-109（本地变更捕获）、ADR-110（退出不注销同步根）、
  `docs/roadmap.md`（S1 单向 remote→local）、本仓 `nativesync/src/manager.rs`（`sync_now` 现行为 BFS 全树）

## 1. 背景与目标

用户的原话：同步这件事对用户应该**几乎无感**——不用点「立即同步」，云端的变化自己能跟上。
S1 的现状是：只有手动 `sync_now`（BFS 全树递归列一遍）。本 ADR 把"必须点一次"变成"可选的诊断入口"：
**云变 → 本地自动跟上**（S1.5）。**范围纪律**：不含上传方向（S2/S3）、不含冲突处理；只是单向 remote→local 的自动对账。

## 2. 七个问题的逐项决策

### 2.1 触发源（问题 1）

**决策**：**启动后定时轮询**为主触发源；启动后**不设额外事件源**。可选：授权完成/重新启用 NativeSync 时立即补一次（复用同一路径）。

- 百度消费级网盘**没有 webhook / 推送**。依据：百度网盘开放平台文档只提供 REST 拉取式接口
  （`method=list` 获取文件列表、`method=meta/filemetas` 查询元信息、下载接口）；检索其
  开放平台接口目录，**不存在**文件变更订阅/推送/webhook 类接口。⇒ **只能轮询**。
- 不引入 CF 回调当触发源：现有 CF 通知（ADR-109）是**本地**变更的捕获，不是云端变更的信号，不能当同步触发器。

### 2.2 增量策略（问题 2，最关键）

**决策**：**"便宜的先查、贵的不做"——两层结构：每层对账 = 根目录一次（快查）+ 有界的交错深扫（分批）**。

1. **每层一次根目录快查（1 次 API 调用）**：`method=list` 取同步根第一层（`order=time&desc=1, limit=100`），
   与索引里 `remote_entry`（该父级的全部条目）按 `(fs_id, size, md5/mtime)` 比对。
   这一层就能立刻发现：**顶层条目的新增/删除/改名/内容变化**。代价：每层 1 次调用。
   **顶层翻页缺口（终审补记）**：顶层条目 **>100** 时单页快查会漏检 ⇒ 顶层快查必须按 `has_more`/`start` **翻页取尽**，翻页调用**计入**每层 25 次上限（超出部分推迟到下一层，同 §2.7 降级纪律）。
2. **交错深扫（分批、有界）**：维护一个**深扫游标**（按目录轮转），每层最多列 `K=20` 个目录，
   把全部目录 `D` 的完整覆盖摊到 `ceil(D/K)` 层。深扫到的目录同样与索引比对：
   一致 ⇒ 本轮该子树标"干净"；不一致 ⇒ 记入差异（新增/删除/改名/内容变化）并收敛到同一套落库/占位符/通知逻辑（复用 §2.4 的同一条路径）。
3. **每层调用上限**：`≤ 1 + 4 + 20 = 25` 次（1 根查 + ≤4 次根查发现的可疑顶层目录**定向下钻** + ≤20 次交错深扫）。
   上限超出的部分推迟到下一层。

**权衡与依据（这是设计里最容易"想当然"的地方，必须写实）**：
- **不能用"父目录签名"省掉子树**：目录的 `mtime` 在子项增删改时**不一定**变化（百度未承诺目录 mtime 反映子项变动），
  所以"看到父目录没变就跳过整棵子树"**不可靠**——这是不引入它的唯一原因，不写"应该可以"。
- **不能问百度"自上次以来的变更"**：开放平台**没有**全局 change-cursor/事件流接口 ⇒ 无法做真正的增量。
- **md5 可得性（终审补记）**：比对键 `(fs_id, size, md5/mtime)` 以 `method=list` 响应**稳定携带 md5** 为前提，**实现期须先验证**；若 `list` 不带 md5，比对键退化为 `(fs_id, size, server_mtime)`——“内容变了但 size 与 mtime 都未变”会漏检，裁决为**可接受残余风险**（该情形概率极低），**不做** filemetas 补查（否则每层调用数翻倍，破坏配额预算）。
- 因此诚实的省法是 **交错覆盖**（把 `D` 次目录列举摊到多层）+ **根查快查**（顶层变化在 1 层内被发现）。
  深查的**检测延迟 = ceil(D/K) × 层间隔**，换来的是每层 ≤25 次调用（配额安全）。

### 2.3 间隔与退避（问题 3）

**决策（默认值，均可配置）**：
- **首次**：启动后 **60 秒**（让授权/连接/注册先稳定，不与启动路径抢锁/抢网）；
- **之后每层间隔**：**10 分钟**；
- **失败退避**：连续失败按 **2m → 4m → 8m → 封顶 60m** 指数退避；一次成功即复位到 10 分钟；
- **授权失效/网络不可达**：**不重试风暴**——按上述退避；连续 **≥5 次**失败 → 暂停自动对账，
  状态进入 `auto_sync_paused`，等手动「立即同步」成功或授权恢复后再自动恢复。

**取值依据**：
- 调用量上限：每层 ≤25 次 ⇒ ≤150 次/小时 ⇒ ≤3600 次/天——消费级网盘的拉取式配额下**显著安全**；
  10 分钟既给足了授权/连接的稳定性，又把顶层变化延迟压在 10 分钟内。
- 退避封顶 60m 与"≥5 次即暂停"是防"重试风暴烧配额 + 刷日志 + 骚扰"三道防线的最小组合。

### 2.4 与手动「立即同步」的关系（问题 4）

**决策**：**同一条代码路径**（一条对账引擎），手动是这条路径的一次**全量触发**；自动是它的**增量触发**。

- 手动「立即同步」与自动对账**共用** `sync_now`/对账引擎（差异只在"全量 vs 增量"这一个开关上），**不许两套逻辑分叉**。
- **单飞 + 抢占/合并**：任何时刻最多一层对账在跑；手动触发时——
  - 若一层自动对账**正在跑** → 取消它、立即以手动层替代（**抢占**）；
  - 若已有**待跑**的手动请求 → 合并为一个（**合并**），而不是排队几十次。
- 「立即同步」**降级为诊断/应急位**：保留但不再强调（它正是"把必须点变成可选"的落点）。

### 2.5 失败与可观测性（问题 5）

**决策**：失败**可见但不骚扰**；绝不弹窗打断用户。

- 失败写日志 + 状态位：`last_sync_at`、`last_error`、`consecutive_failures`、`backoff_until`、`auto_sync_state`
  （`ok`/`backing_off`/`paused`）——沿用现有 `pandock://nativesync/state` 事件面（不新增通道）。
- **只有连续失败到阈值**（默认 **≥5 次**，或连续失败 **≥1 小时**）才在设置页给一个**非模态**的提示位
  （chip/banner，例如「自动对账已暂停：授权或网络异常」），**绝不弹窗**。
- 用户可用配置 `native_sync_auto=false` 关掉自动对账（回到纯手动）。

### 2.6 对 UI 的要求（问题 6，给后续 UI 切片的输入）

**决策**：状态**自动更新**；给用户一个"上次对账时间/结果"的可见信息；「立即同步」移入诊断/应急位。

- 设置页 NativeSync 区块自动跟随 `pandock://nativesync/state`（已有），不需要用户点刷新。
- 新增**一行**状态信息：「上次对账：`HH:mm:ss` · 结果：`ok/失败原因`」（来自 §2.5 的状态位），
  自动对账层结束时更新；失败阈值到达时这行**就是**那个非模态提示位。
- 「立即同步」按钮保留但**降级**为诊断/应急（文案可改为「立即对账（诊断）」），不再作为"必须点"的主入口。

### 2.7 性能边界（问题 7）

**决策（数量级估算）**：以 1000 条目、约 50 个目录、10 层深度为例：

| 路径 | 每层调用数 | 耗时量级 | 覆盖/延迟 |
|---|---|---|---|
| 现有全量 BFS | D = 50 次 list（+ 仅变更文件的 filemetas） | 网络受限，约 10–30 秒 | 每次触发即全量 |
| 本设计：每层根查 + 定向 + 交错 | ≤ 1 + 4 + 20 = 25 次 | 约 5–15 秒/层 | 顶层 ≤ 1 层延迟；深层 ≤ ceil(50/20)=3 层 |
| 触发"停止下钻/降级"的条件 | 见下 | — | — |

- **停止下钻 / 降级条件**：
  - 单层调用数超过 **25** → 剩余目录**推迟到下一层**（不爆配额）；
  - 目录总数 `D > 500`（大树）→ 交错批量 `K` 减半（20 → 10），并把间隔拉长（10m → 15m）；
  - 连续失败 → 走 §2.3 退避与暂停，而不是继续下钻。
- 深度（10 层）不改变**每层**调用数（`D` 不变），只影响**完整覆盖所需层数**——这是交错覆盖的固有延迟，
  也是"配额安全"换"检测延迟"的明码。

## 3. 实现序（提示，不在本 ADR 承诺交付）

1. 对账引擎参数化（全量 vs 增量开关）+ 交错游标持久化（SQLite，重启续扫）；
2. 调度器（首次 60s、10m、退避、暂停、单飞抢占/合并）；
3. 状态位与事件面（`last_sync_at/last_error/consecutive_failures/backoff_until/auto_sync_state`）；
4. UI（状态行 + 诊断位 + `native_sync_auto` 开关）。

## 4. 不做的事（范围纪律）

- 不含上传方向（S2/S3）与冲突处理；
- 不引入 webhook/推送（百度没有）；
- 不把「立即同步」删除——它降级为诊断/应急入口。

## 5. 风险与回滚

- **风险**：配额误判（交错批量过大）⇒ `K`/间隔都可配置，默认保守（K=20、10m）；
  授权/网络异常期自动暂停 ⇒ 不会烧配额或刷爆日志；交错游标错位 ⇒ 可从索引重建（full pass 兜底）。
- **回滚**：`native_sync_auto=false` 即回到纯手动；设计全部落在 nativesync 的既有对账引擎上，不碰 WebDAV/auth。

## 6. 决策点落档（2026-10-13 开发总监终审裁决）

- 每层调用上限 **25**、间隔 **10 分钟**、退避封顶 **60m**、暂停阈值 **5 次**——按默认值**定稿**；
- 交错深扫 **K=20** 与定向下钻 **≤4** 的分界——**定稿**；
- 「立即同步」降级文案与「上次对账」一行的形态——**已裁决：交由后续 UI 切片定稿**（本 ADR 不定稿）；
- 终审补记两处已并入正文 §2.2：**顶层翻页缺口**（翻页取尽、计入 25 次上限）与 **md5 可得性**（退化为 `(fs_id, size, server_mtime)`，可接受残余风险）。
